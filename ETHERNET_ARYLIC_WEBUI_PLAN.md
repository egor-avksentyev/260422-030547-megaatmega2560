# План: Ethernet на Mega — метадата Arylic + веб-управление

Статус: **только план, ничего не реализовано и не куплено/распаяно**. Финальное архитектурное
решение (после сравнения с вариантом Wi-Fi/ESP32, см. историю обсуждения) — **Ethernet напрямую
на Mega, одна прошивка, без второго чипа**. Записано, чтобы не забыть — вернуться к этому файлу
перед началом работы.

## Почему Ethernet, а не Wi-Fi/ESP32 (и почему не забыли про Wi-Fi совсем)

Рассматривался вариант с ESP32 (Wi-Fi + captive portal для ввода пароля при переезде между
квартирами, Mega только слушает готовые данные по UART). Решили в пользу Ethernet, потому что:

- **Один чип, одна прошивка** — вместо двух прошивок и протокола между ними. Меньше суммарной
  сложности и точек отказа, даже если Mega формально "нагружается больше", чем в схеме с ESP32.
- **Не боится металлического корпуса** — Wi-Fi там глушится (клетка Фарадея), нужна была бы
  внешняя антенна с выводом наружу. Кабелю/разъёму RJ45 корпус не мешает вообще.
- **Не боится просадок питания от реверса моторов** — Wi-Fi даёt пики тока 300-500мА на
  передаче, что могло совпасть с известной, измеренной просадкой линии 5В при развороте
  H-моста (см. `MOTOR_REVERSE_BRAKE_MS`, `hardware_settings.h`). У Ethernet-модуля таких
  пиков нет.
- **Не требует повторной настройки при переезде** — DHCP сам выдаёт адрес при подключении
  кабеля, никакого captive portal/ввода пароля заново каждый раз.
- Оценка по ресурсам Mega (см. ниже) показала, что для этой задачи ей **не нужен** второй,
  более мощный чип — резерва хватает с запасом.

**Единственный реальный минус Ethernet** — нужен второй физический порт/кабель в месте
установки (Arylic туда уже заведён проводом). Решается недорогим неуправляемым свитчем рядом
с устройством (один входящий кабель → два коротких кабеля: на Arylic и на эту плату), если в
месте установки в принципе есть возможность завести хотя бы один Ethernet-кабель. Если у
конкретной инсталляции такой возможности нет вообще — тогда актуален вариант с Wi-Fi/ESP32,
но для текущей инсталляции пользователя кабель провести можно.

## Почему не через UART к Arylic (см. память проекта)

Раньше уже была похожая идея — читать метадату с Arylic через UART напрямую. Отклонена: тот
конкретный модуль, что стоит у пользователя, по UART молчит, апгрейд/реверс-инжиниринг не
окупаются. **Эта идея — принципиально другой канал**: не UART модуля, а локальная сеть +
HTTP API самого Arylic (LinkPlay-платформа, `httpapi.asp?command=getPlayerStatus` и
подобное) — ограничение из прошлой попытки тут не действует.

## Цели (две функции, обе на одном Ethernet-модуле)

1. **Метадата Arylic** — пока играет STREAMER, опрашивать локальный HTTP API Arylic, показывать
   трек/исполнителя на OLED; автоматически щёлкать реле переключения источника на STREAMER,
   когда там стартует поток (детали поведения — открытый вопрос, см. ниже).
2. **Веб-управление** — простая HTML-страница с телефона (те же действия, что сейчас доступны
   с пульта: Right/Left/Enter/Up/Down/Mute/Power/Set), плюс отображение текущего статуса
   (что на экране/громкость/источник).

## Архитектура — одна прошивка на Mega

Никакого второго чипа. Модуль **W5500** (Ethernet, SPI) висит на той же Mega, управляется
штатной библиотекой `Ethernet.h` напрямую из существующей прошивки:

- **HTTP-клиент** (`EthernetClient`) — периодический запрос к Arylic, разбор ответа
  (JSON/hex — уточнить точный формат конкретно под свой модуль через браузер/`curl` по IP
  устройства, когда дело дойдёт до реализации).
- **HTTP-сервер** (`EthernetServer`, порт 80) — отдаёт HTML-страницу управления, принимает
  команды (`GET /cmd?action=right` и т.п.), отдаёт статус по опросу (простой `fetch()` раз в
  1-2 секунды с телефона, без WebSocket — тот ощутимо сложнее и не нужен для этой задачи).
- Оба назначения — на одном чипе W5500, у него 8 аппаратных сокетов, с запасом хватает на
  клиентское соединение к Arylic и серверные соединения от телефона одновременно.
- **Обязательно неблокирующая реализация сервера** — на каждой итерации `loop()` только
  проверка "есть ли новый клиент" и пошаговая обработка, никаких `while(client.connected())`
  синхронных ожиданий. Это принципиально для этого проекта — вся сегодняшняя работа с ИК была
  именно про то, чтобы ничего не блокировало `loop()` надолго; веб-сервер не должен свести
  этот эффект на нет.
- HTML/CSS хранить в **PROGMEM** (флеш), не в RAM — RAM здесь узкое место, флеш — нет.
- Команды с веб-страницы должны дёргать **те же функции-действия**, что сейчас вызывает
  `case IR_RIGHT:`/`IR_LEFT:` и т.п. в `remote_control.cpp` — не третья копия логики, а общий
  вызов из разных источников ввода (пульт/энкодер/веб).

## Железо

- Модуль **W5500** (Ethernet, SPI) — при выборе платы предпочесть вариант, явно заявленный
  как **5В-совместимый** (многие готовые W5500-брейкборды уже имеют на борту свой стабилизатор
  и согласование уровней специально под прямое подключение к 5В Arduino) — тогда отдельный
  внешний стабилизатор 3.3В и level shifter, обсуждавшиеся для варианта с ESP32, **не
  понадобятся вообще**. Проверить конкретно по даташиту/описанию выбранной платы перед
  покупкой — если найдётся именно такая, весь раздел питания/уровней из Wi-Fi-варианта плана
  снимается сам собой.
- Если попадётся только "голый" 3.3В-модуль без согласования — тогда те же правила, что
  обсуждались для ESP32 (отдельный стабилизатор с хорошей реакцией на броски, конденсаторы на
  входе/выходе, level shifter на линии SPI) остаются в силе, просто пики тока у Ethernet
  меньше, чем у Wi-Fi, так что требования к стабилизатору мягче.
- SPI-шина уже используется дисплеем (пины 50-52, MISO/MOSI/SCK) — W5500 можно повесить на ту
  же шину, у каждого устройства свой CS-пин, разделение шины между несколькими SPI-устройствами
  — стандартная, ничем не рискованная практика.
- Кабель RJ45 до места установки (см. раздел выше про свитч, если там только одна точка
  подключения).

## Открытые вопросы (не технические — вопрос предпочтений, решить до/во время реализации)

1. **Автопереключение источника** — если сейчас выбран, например, AUX, а на Arylic стартовал
   поток — переключать источник молча сразу, или только при определённых условиях (например
   только из Standby, или отдельным тумблером "автослежение вкл/выкл" в меню)?
2. **Как показывать метадату на OLED** — отдельный новый пункт меню (добавлять **строго в
   конец** `menuItems[]`, не в середину — иначе поедут места, завязанные на фиксированные
   индексы Bass=0/High=1/Volume=2, см. `main.cpp`, оверлей вращения ручек) или автоматический
   оверлей, когда Source == STREAMER и статус == playing?
3. **IP-адрес Arylic-устройства в локальной сети** — зашить фиксированный (проще, требует
   DHCP-резервации на роутере под MAC Arylic) или искать автоматически (mDNS/SSDP — надёжнее
   при смене сети, сложнее реализовать; можно отложить, начать с фиксированного IP как MVP).
   Свой собственный IP Mega получает по DHCP автоматически через `Ethernet.h` — тут вопросов нет.
4. **Поведение при потере данных** — что показывать, если поток остановился, кабель
   отключился, или Arylic не отвечает.
5. **Доступ к веб-интерфейсу** — открытый в локальной сети без пароля (проще, обычно
   достаточно для домашней сети) или с простой защитой (базовая HTTP-авторизация)?

## Оценка нагрузки на Mega

Актуальные цифры на момент написания плана (после замены IRremote на ICU-декодер):
Flash — 101КБ из 254КБ занято (~153КБ свободно), RAM — 3.46КБ из 8КБ занято (~4.7КБ свободно).

Обе функции (HTTP-клиент к Arylic + неблокирующий HTTP-сервер с простой страницей на
PROGMEM) по объёму сравнимы с уже написанным модулем `rc5_icu.cpp` — с большим запасом
укладываются в свободный резерв. Отдельного второго чипа под это не требуется.

## Риск для уже написанного кода

Низкий, если новый пункт меню (если он будет) добавлять в конец массива, а не в середину.
Места, которые реально трогают уже работающий код:
- Автопереключение Source (открытый вопрос 1) — нужно аккуратное, явное условие, а не
  безусловная перезапись выбора пользователя.
- Веб-команды становятся **третьим** параллельным источником ввода (после пульта и энкодера)
  — тот же принцип дублирования, что уже описан в проекте для пульта/энкодера
  (`remote_control.h`: "при изменении поведения пункта меню правь оба пути параллельно"),
  теперь распространяется на три пути, а не два.
